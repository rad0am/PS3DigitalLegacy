# PS3 Digital Legacy

## What this app is

A static website (hosted on GitHub Pages) that lists games and DLC available **only digitally** on the PlayStation 3 and PlayStation Vita PlayStation Stores. Both stores are expected to close (Sony says from July 2027, no exact day), so the site lets users:

- browse a catalog of such titles (search, filters, sorting),
- add games to a "want to buy" list and mark them as "bought",
- sign in and sync that list across devices,
- see a countdown to the store closure.

This is a fan project, not affiliated with Sony. The site sells nothing; it only informs users what can still be bought and where.

All code, identifiers, comments, docs and commit messages are in **English**.

## Stack

The owner's choices are **Svelte**, **TypeScript** and **Firebase**. Do not propose other frameworks or languages.

- **Svelte 5** (runes) with **TypeScript** (strict) on **SvelteKit 3** with `adapter-static`. All routes are prerendered (`src/routes/+layout.ts`), because Pages has no SPA fallback. SvelteKit is configured in `vite.config.ts` (Kit 3 has no `svelte.config.js`). `paths.base` comes from the `BASE_PATH` env var (CI sets it to `/<repo>`; local dev uses the root). App code is imported through the `#lib/...` alias.
- **Firebase** (client only, no custom backend): **Authentication** (providers: Google, Discord, Facebook and Reddit, see "Sign-in providers") and **Firestore**.
- **Deploy:** GitHub Actions, a push to `main` publishes the site.
- Tooling: Node 22+ (`.nvmrc`), npm, ESLint + Prettier, Vitest. Commands: `npm run dev`, `build`, `check`, `lint`, `format`, `test`. CI (`.github/workflows/ci.yml`) and deploy (`deploy.yml`) run lint, check, test and build.

## Data: `ps3-digital.json` and `psvita-digital.json`

One file per platform in `data/`: `ps3-digital.json` and `psvita-digital.json`, outside `static/` on purpose (they must never be shipped as one 17 MB payload). They are generated by a script, so do not hand-edit them without a reason. Sizes are about 10 MB (PS3) and 7 MB (Vita). Prettier, ESLint and `.gitattributes` treat both as generated.

Structure of each file: `{ schemaVersion, generatedAt, games: Game[] }`. Every game in a file has the same `platform`.

| As of 2026-11                               | PS3 (2026-11-02) | PS Vita (2026-11-16) |
| ------------------------------------------- | ---------------- | -------------------- |
| games                                       | 894              | 894                  |
| `digitalOnly: true`                         | 682              | 660                  |
| DLC (games with DLC)                        | 3,104 (325)      | 8,198 (308)          |
| games with prices (currencies)              | 606 (33)         | 531 (31)             |
| `psnprofilesUrl` / platinum                 | 770 / 256        | 734 / 434            |

Game `id`s are unique across both files (checked: no overlap), so the user list stays one flat map keyed by `id` with no platform prefix. 109 titles (115 by `igdbId`) exist on both platforms as separate entries with different ids.

### Implications for the app

- **17 MB is too much to ship as one payload.** At build time, read both files, generate one lightweight index (id, platform, title, regions, type, genres, price in PLN/EUR/USD, cover, status, DLC count) and load details (description, screenshots, full DLC list and prices) lazily, per game. Gzip on Pages helps but is not enough. DLC grew from about 3,100 to 11,302 entries, so measure the index size after adding Vita and, if the DLC rows push it too far, split the DLC index per platform and load it only when the DLC type is selected.
- **Free DLC:** 1,762 DLC (248 PS3, 1,514 Vita) have a price of 0. Show "Free" (localized), never "0.00 USD".
- **Prices for a different edition:** Vita `notes` often say `Store prices are for "<title>"`. Show those notes on the game page as they are.
- Currency is user-selectable with a browser-based default; see "Currency selection".
- Surface `storeStatus: "delisted"` and `"unknown"` clearly, so users know a game may no longer be purchasable.
- Covers and screenshots come from `images.igdb.com`. Load them lazily (`loading="lazy"`) and handle errors with a placeholder. Do not copy them into the repo (copyright).
- Add data validation (JSON Schema, e.g. `ajv`) as a CI step. An invalid file must never reach production.

## Platforms (PS3 and PS Vita)

The design (`design/`, see its README) treats the two platforms as one catalog with a platform dimension. Nothing is split into separate sites or routes.

- **Platform badge** on every game row, card, search result and details page: PS3 solid dark, PS VITA solid blue (`--vita`), label only. The label carries the meaning, colour does not.
- **Catalog filter:** "Platform" is the first filter group (checkboxes on desktop, pills in the mobile sheet), default both selected. A chip "Platform: PS Vita" shows when only one is selected. The selection lives in the URL (`?platform=ps3|psvita`, absent means both) so Home tiles and shared links work.
- **Home:** copy, stats and the closure banner name both platforms; a "Browse by platform" section has one tile per platform linking to `/catalog?platform=...`. "Today's picks" and "Trophy hunters" draw from both platforms and show the platform in the meta line.
- **My list:** progress is shown per platform (PS3 and PS Vita bars for digital-only games, and for DLC), and a platform pill filter (All, PS3, PS Vita) sits above the Want to buy / Bought tabs. The two progress indicators from "Features" stay (games, DLC), each split by platform; totals: 1,341 games and 11,302 DLC.
- **Same game on both platforms:** separate entries with separate ids. Search lists both, each with its badge. The details page shows an "Also on" link to the other platform's entry, matched by `igdbId` (only when both exist). Do not merge entries or share state between them.
- **Search** covers both platforms; no platform scoping in the modal. Use the catalog filter for that.
- **Validation:** the JSON Schema accepts `platform` in `PS3 | PS VITA`, checks every game in a file has the file's platform, and fails the build when an `id` repeats across files.
- **Closure:** one countdown for both stores (Sony's notice covers both). If Sony ever gives different dates, `siteConfig` needs a per-platform date; do not add it before then.

## Digital only and physical releases

"Has a physical release" means the **game itself** exists on a disc (PS3) or a game card (PS Vita), `digitalOnly: false`. UI copy says "physical release", not "disc release", so it is correct for both platforms. Such a game may still have **DLC that can only be bought digitally**, and that DLC is exactly what this site is about.

- **DLC is always digital only.** DLC cannot be bought physically, so every DLC entry counts as digital only regardless of its parent's `digitalOnly`. The "Digital only" filter applies to games, never hides DLC.
- **Default view:** games with `digitalOnly: true`, plus all DLC when the type filter includes DLC.
- **Games with a physical release and DLC stay reachable.** With "Digital only" on, the game is hidden as a game row but its DLC is still listed under the DLC type, each entry naming its parent game. The game's details page is still reachable (from DLC rows and from search).
- **With "Digital only" off**, physical-release games appear with a neutral "Physical release" badge and a count such as "6 DLC, digital only". The base game has no digital price to show, so the row shows "DLC from <lowest DLC price>" or "Price unavailable".
- **Game details of a disc game** shows a note: "This game has a physical release (disc or game card). Only its DLC is available digitally." The existing note for a disc that exists only in another region stays: "A physical release exists in another region."
- The sidebar toggle's helper text says: "Hides games that have a physical release (disc or game card). Their DLC stays listed."
- Do not claim the base game cannot be bought digitally; the data only says a physical release exists. Wording stays neutral.

## User state: local-first

- A Svelte store persists to `localStorage`. The app works fully without signing in.
- Shape: `{ [gameId]: { status: 'wishlist' | 'bought' | 'none', updatedAt: number } }`. `none` is a tombstone for an entry the user removed: without it, the merge would bring a deleted entry back from the other side. Tombstones are not exported and are pruned after 90 days.
- On sign-in, **merge**: union of local and remote entries; on conflict the newer `updatedAt` wins per `gameId`. Never blindly overwrite either side.
- Firestore: one document `users/{uid}` holding a map of games. Rules: read and write only when `request.auth.uid == uid`.
- The Firebase config (`apiKey` etc.) is public by design. Security comes from the rules.
- In the Firebase console, add `<login>.github.io` to Authorized domains.

### Sync strategy and Firebase setup

- **Writes:** a change goes to `localStorage` immediately. When signed in, it is marked dirty and sent to Firestore with a debounce, never more often than every 10 seconds. Send the whole `users/{uid}` document in one write, and skip the write when nothing changed.
- **`lastWrite`:** every write sets `lastWrite: serverTimestamp()`. `firestore.rules` rejects a write that does not, and rejects an update less than 10 seconds after the previous one. On a rejected write, retry later and never drop local data. Try a best-effort flush when the page is hidden.
- **Reads:** one read after sign-in, then merge as described above. No realtime listeners, to save quota.
- **Plan:** the Firebase project is `ps3digitallegacy` on the free **Spark** plan. Never upgrade to Blaze or link a billing account without the owner's agreement; Spark cannot charge, it only stops serving when a daily quota runs out (the app keeps working locally).
- **Rules:** `firestore.rules` is the source of truth but is published by hand in the Firebase console (Firestore Database, Rules). Changing the file does not update the live rules.
- **App Check:** deliberately not used. The only supported web provider is reCAPTCHA Enterprise, which may require billing. Do not enable it without the owner's agreement.
- **Config:** the public web config lives in `src/lib/firebase/config.ts`, not in `.env` (it is shipped to the browser anyway). `.env` stays for real secrets only. Access Firebase through `getFirebaseApp`, `getFirebaseAuth` and `getFirestoreDb` in `src/lib/firebase/client.ts`; they run only in the browser because all routes are prerendered.

## Currency selection

Users can choose the currency in which prices are shown. The data has prices in 33 currencies (`prices: { currency, amount }[]`), so the selector offers exactly the currencies that occur in the data. Derive that list at build time; do not hard-code it.

**Default currency:**

1. Saved user choice (`localStorage`, and the Firestore user document when signed in).
2. Otherwise derive it from the browser: take the region from `navigator.languages` (e.g. `pl-PL` -> `PL`, `en-GB` -> `GB`, `de-DE` -> `DE`) and map the region to a currency with a small static region-to-currency table (browsers expose no currency API). Use the first entry in `navigator.languages` that yields a currency present in the data.
3. If nothing matches (no region in the locale, unknown region, currency not in the data), use **USD**.

Eurozone countries map to `EUR`. The table is a plain TypeScript map and must be unit-tested.

**Fallback when a game has no price in the selected currency:**

1. Selected currency.
2. `USD`.
3. `EUR`.
4. Show "price unavailable" (localized).

When a fallback currency is shown, label it explicitly (e.g. "9.99 USD"), never silently mixing currencies in a list. Do not convert between currencies; show only prices that exist in the data.

Data facts that justify the chain (as of 2026-11): PS3: 606 of 893 games have prices and 287 have none; USD is missing for 73 of the priced games; only 4 priced games have neither USD nor EUR. PS Vita: 531 of 894 have prices and 363 none; USD is missing for 177 of the priced games and 84 have neither USD nor EUR, so the EUR step helps less and "price unavailable" shows more often on Vita. The union of both files is still 33 currencies.

Format amounts with `Intl.NumberFormat` using the active UI locale and the displayed currency. Currency choice is independent of the UI language: a Polish-language user may still pick USD. Treat prices as informational ("last known price"), because the store may close or change prices.

## PSNProfiles link

Each game can show a button linking to its PSNProfiles trophy page, so users can check whether the platinum trophy is still obtainable (for example when online servers are gone or trophies are marked unobtainable there).

- Source field: `psnprofilesUrl`. In the current data 1,504 of 1,787 games have it (770 PS3, 734 Vita; all on `psnprofiles.com`); 283 have none. Every game with `trophies.hasPlatinum: true` (690 games, 256 PS3 and 434 Vita) has a URL.
- Render the button only when `psnprofilesUrl` is set. Do not show a disabled or broken button for the 123 games without one.
- Give extra prominence to the button when `trophies.hasPlatinum` is `true`, since that is the case the user cares about. Games with `trophies.supported: false` show no trophy info.
- **The app does not determine whether a platinum is obtainable.** It only links to PSNProfiles, which is the source of truth. Do not display claims like "platinum obtainable" or "unobtainable" derived from our data. Wording must be neutral, e.g. "Check platinum status on PSNProfiles".
- Open the link in a new tab with `target="_blank"` and `rel="noopener noreferrer"`. Validate at build time that the URL host is `psnprofiles.com` before rendering.
- The label, tooltip and `aria-label` come from the i18n catalog (both `en` and `pl`). The site name "PSNProfiles" is not translated.
- DLC entries have a `trophies` field but no URL of their own; link DLC trophy checks to the parent game's `psnprofilesUrl`.
- Use a plain link, not an embed or API call. Do not scrape PSNProfiles or copy its content into the repo.

## Add to Basket and store data

The game details page has an "Add to Basket" button that works like the one on https://ps-store-searcher.pages.dev/ (a third-party site; we copied its behavior, not its code). It is a plain link to `https://checkout.playstation.com/add/<sku>?clientId=<id>`, the URL the PlayStation Store website itself builds. The user must be signed in to the store in the same browser and the PSN account must belong to the same store region as the SKU. Default `clientId` is the web client `2eb25762-877f-4140-b341-7c7e14c19f98` (`WEB_CLIENT_ID` in `src/lib/store.ts`); `?clientid=...` on the site's address overrides it.

- SKUs live in `storeSkus` on each game, one per store catalog: `NA` (US, CA, BR, MX, HN), `EU` (Europe, Oceania, South Africa, India, Israel, Turkey, ...), `JP`, or a currency code (KRW, HKD, SGD, TWD, THB, MYR, IDR, AED, SAR) for stores with their own catalog. SKUs differ per catalog; `src/lib/store.ts` maps the selected currency to the catalog and `basketOptions` puts that store first. When the selected store has no SKU, the button shows another store and the note says it works only with an account of that region.
- Do not hide the risk: Sony's terms may treat buying PS3 and Vita content through the web store as not allowed. The About page ("About the Add to Basket button", `#basket`) says so, and the button links there. The site still sells nothing and does not process any purchase.
- DLC has `storeSkus` too (same keys) and a compact basket button in the DLC list of the game page. Only about a third of the DLC have one (PS3 1,728 of 3,095, Vita 2,130 of 8,198, as of 2026-11): a DLC gets a SKU only when its parent game was found by exact title in a store and the DLC name matched an add-on of that product (optionally without the game title in front). Catalog DLC rows have no basket button.

**Scripts** (Node 26 runs the `.ts` files directly; they are type-checked by `npm run check`):

- `scripts/fetch-store-data.ts --platform ps3|psvita` crawls the unofficial store API (`commerce1.api.np.km.playstation.net/store/api/chihiro/00_09_000`). It searches each game by exact normalized title in one store per shared catalog (US, GB) and in each own-catalog store, takes the SKU, then fetches that product's price in every store of the shared catalog (`container/<CC>/<lang>/19/<productId>`). A result must be a game-type product playable on the game's platform; ambiguous matches are skipped. Output goes to `.store-cache/<platform>.json` (ignored by git, resumable). About 6 to 8 seconds per game; polite rate limit (one request per 60 ms overall).
- `scripts/apply-store-data.ts --platform ps3|psvita` merges the results into `data/*.json`: adds only prices for currencies the game does not have yet (existing prices are never changed), sets `storeSkus`. It keeps each file's own formatting (the PS3 file uses 4 spaces, `42.0` amounts and `'` escapes; the Vita file uses tabs), so the diff holds only added data. Use `--dry-run` first.
- API facts: `price` is in minor units (`999` = 9.99), but not for every currency (INR comes as `900` for "Rs 900"), so the amount is cross-checked against `display_price`. In a pilot, all 175 prices that the data already had matched the API exactly.
- `scripts/fetch-dlc-store-data.ts` does the same for DLC: a game's product page lists all its add-ons, so it takes one search and a few `container` requests per game and catalog (NA, EU, JP), not one per DLC. It also records the DLC price in the searched store (USD, GBP, JPY). `apply-store-data.ts` merges it when `.store-cache/<platform>-dlc.json` exists.
- Not covered: DLC prices in the other stores (about 11,000 entries, one request per store each), and games the store no longer lists.

## Internationalization (i18n)

The UI ships in **28 languages**, chosen to cover every currency in the data (all 33): `en` (source and fallback), `pl`, `ar`, `cs`, `da`, `de`, `el`, `es`, `fi`, `fr`, `he`, `hi`, `hu`, `id`, `it`, `ja`, `ko`, `ms`, `nb`, `nl`, `pt` (Brazilian wording), `ro`, `ru`, `sv`, `th`, `tr`, `uk`, `zh-Hant`. Adding a locale means: a message file, an entry in `project.inlang/settings.json`, an entry in `src/lib/languages.ts` (native name, Intl tag, currencies, `rtl`) and the `i18n:compile` script keeps working unchanged. Non-English and non-Polish catalogs were machine-translated and have had no native review; corrections are welcome. Arabic and Hebrew are right-to-left (`dir` is set on `<html>`). The picker is a searchable list (`LangSwitch.svelte`, design in `design/.preview/Language.html`).

- Use a type-safe i18n library that works with Svelte and static output. Recommended: **Paraglide JS** (tree-shakeable, typed message keys); `svelte-i18n` is an acceptable alternative. Pick one and do not mix.
- **No hard-coded UI strings** in components. Every user-visible string goes through the message catalog (`messages/en.json`, `messages/pl.json`), including `aria-label`s, placeholders, empty states and error messages.
- Locale detection: saved choice in `localStorage` first, then `navigator.language`, then `en`. Provide a language switcher. For signed-in users the choice may also be stored in the user's Firestore document.
- Decided: switch locale on the client (no per-locale routes). Paraglide strategy is `localStorage`, then `preferredLanguage`, then `baseLocale` (set in `vite.config.ts` and the `i18n:compile` script, keep them identical). Messages live in `messages/{en,pl}.json`.
- Format numbers, dates, prices and plurals with `Intl` APIs and the active locale. Polish has more than two plural forms, so use ICU/plural rules instead of `count === 1` checks.
- Currency is independent of the UI language; see "Currency selection".
- **Game data is not translated.** Titles, descriptions and genre names from the data files come from IGDB in English and are displayed as they are. Only the application's own UI text is localized. Genre names used as filter labels may be mapped to translated labels if needed.
- Keep the key sets of all message files identical to `en.json`, with the same `{placeholders}`. `src/lib/i18n.test.ts` checks both for every locale in `project.inlang/settings.json`, so CI fails on a missing or extra key. Plural messages use the CLDR categories of each language.

## Store closure countdown

Sony's official notice (https://www.playstation.com/en-us/support/important-notice/, checked 2026-11) says the PS3 and PS Vita stores close "starting July 2027", with no exact day. Two config fields in `src/lib/config.ts`: `closingMonth` (`'2027-07'`, shown as "Store closing: July 2027. The exact date is not announced yet.") and `closingDate: string | null` (exact day). When `closingDate` is set, the countdown starts and replaces the month text. `closingDate` states:

- `null`: show the announced month if `closingMonth` is set, otherwise "closing date not announced".
- future date: show a countdown in days and hours.
- past date: show a "store closed, this is an archive" state.

Do not enter a date without an official announcement from PlayStation.

## Working rules

- Deploy a skeleton to Pages first, then add features. The skeleton is in place (`src/routes/+page.svelte`).
- Small, separate commits. Do not commit or push without an explicit request.
- **The `.env` file is in `.gitignore` and contains secrets. Never read, print or commit it.** Keys (e.g. for IGDB) are used only for generating data and must never end up in site code.
- Do not add a backend or paid services without agreement. The whole project must fit in free plans (GitHub Pages, Firebase Spark).
